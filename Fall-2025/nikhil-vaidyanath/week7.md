## Progress
On Sunday, we met as a group and defined the "phases" of interface that the GSAU will engage in. We talked with a member of the verification team who will generally work on verifying GSAU + Systolic Array as a unit. We narrowed it down to three phases: Weights -> Activations -> Psums. The reasoning for this is that weights must precede activations as when we are completing a GEMM/convolution we are using a weight stationary systolic array. Activations can procede thereafter as now that weights are loaded, either the kernel or "B" matrix is ready to MAC against. Once activations are done loading, we're ready to load in Psums into the buffer. We calculated that the fastest path through the systolic array is straight down (32 cycles) and the slowest is all the way to the right and then straight down (64 cycles). Knowing this information, that tells us we have the time to load in partial sums subsequently after loading activations because the partial products will not have flowed down to the bottom of the systolic array until we are all done loading activations. This "phased" data transfer approach makes verification easier and ensures we are only sending in one set of data at a time (max 32 BF16 values, 512 bits), reducing number of wires compared to simultaneous loading while achieving same throughput. As for the shifting unit, we will likely be using a stripped down version of the Benes network with the number of stages reduced. This will strike a balance between the high latency full Benes network with all permutations available, and the long combinatorial barrel shifter that was considered earlier. We only need to shift right by a fixed value for the current implementation. If we later see a useful workload that requires different shifting behavior, we may make the case to change the implementation.
