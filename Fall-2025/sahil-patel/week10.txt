Progress
This week we refined the packetization design and started using the DAG tools more effectively. We also clarified how vector registers will actually be populated with data.

Scheduler team meeting on sunday told us that the compiler doesn't need to set the dependency check and set bits. Their scheduler will derive those signals directly from the order and contents of the instructions in each packet.

On the packetization side, we are now able to visualize the instruction DAG generated by PPCI using pydot. 
– Packetize by basic block, since PPCI already groups instructions into blocks according to jump structure.
– Inside each basic block, use the DAG level of each instruction to drive packet formation. 

We also received more information on how vector registers will actually receive data on hardware. The plan is to use SDMA instructions to load 2D arrays of bfloat16 values into the vector/register tiles. That led to several concrete tasks:

– Implement an SDMA intrinsic in the frontend so C code can express these transfers.
– Support 2D arrays of bfloat16 as the data format SDMA operates on.
– Introduce or adapt a bfloat16 datatype in the compiler’s IR and backend. We can either base it on the existing float logic (by changing parameters to 16 bits) or introduce a separate type.

This SDMA-based approach is more realistic than trying to emulate a vector LI instruction and fits better with the intended accelerator design.

Next steps
– Implement the bfloat16 datatype in the IR and backend and ensure it can represent 2D arrays of weights.
– Add GEMM and SDMA intrinsics in the frontend and connect them to appropriate IR nodes.
– Use the DAG level-ordering strategy to organize instructions into packets within each basic block, then test this on simple kernels.
